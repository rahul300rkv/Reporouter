What Is llms.txt? How to Make Your Docs Easy for AI to Read

By the Repo Router team·Updated November 17, 2026·5 min read

A website is built for human eyes: navigation, scripts, banners. A language model wants the useful text with as little noise as possible. The llms.txt convention gives AI tools a clean starting point.

What it is

llms.txt is a community proposal, put forward in 2024, for a Markdown file placed at the root of a website or repository. It acts like a curated table of contents for models: a short summary of the project and a list of links to the most important pages. It is a convention rather than an official web standard, and support varies between tools.

The format

The file uses ordinary Markdown with a predictable shape:

  1. A single # heading with the project name.
  2. A blockquote containing a one- or two-sentence summary.
  3. Optional paragraphs of context.
  4. One or more ## sections, each containing a list of links with short descriptions.

Example

# Acme Parser

> Acme Parser is a fast JSON and YAML parsing library for Python 3.10+.

Notes: configuration uses environment variables prefixed ACME_.

## Docs
- [Quickstart](https://example.com/docs/quickstart.md): install and first parse
- [API reference](https://example.com/docs/api.md): all public functions

## Optional
- [Changelog](https://example.com/CHANGELOG.md): release history

Where to put it

  • Website: at /llms.txt, so it loads at the top of the domain.
  • Repository: in the repository root, where tools that read repositories can find it.

Some projects also publish a larger llms-full.txt that contains the complete documentation text in one file, for tools that prefer a single download.

How it helps

Retrieval tools can use the file to decide which pages deserve attention, so answers rely on your best material instead of random pages. Documentation servers such as GitMCP can make use of it when it exists in a repository.

Writing a good one

  • Link to clean, text-first pages, ideally Markdown versions.
  • Write specific descriptions so a model can decide what to open.
  • Keep it short. It is an index, not the documentation itself.
  • Put secondary material under an Optional section.
  • Update it when pages move or are deleted.

Don't expect miracles

It will not fix unclear documentation, and not every AI tool reads it. Think of it as a low-cost improvement that sits alongside a good README and architecture notes, as covered in our repository documentation guide.
