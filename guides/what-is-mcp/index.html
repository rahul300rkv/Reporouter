What Is the Model Context Protocol (MCP)? A Plain-English Guide

By the Repo Router team·Updated November 17, 2026·6 min read

AI assistants are good at language but blind to your world. They do not know what is in your repository, your documentation or your database unless you paste it in. The Model Context Protocol, usually shortened to MCP, is a standard way to fix that.

The problem MCP solves

Before MCP, every connection between an AI app and an outside system was custom work. If you wanted an assistant to read GitHub, search a wiki and query a database, each pairing needed its own integration. With several assistants and several data sources, the number of integrations multiplied quickly.

MCP replaces that tangle with one shared protocol. A data source or tool is wrapped once as an MCP server. Any AI application that speaks MCP, called an MCP client, can then use it without bespoke code.

Where MCP came from

Anthropic introduced MCP as an open standard in November 2024. It is published openly, with specifications, SDKs and reference servers, and it has since been adopted by many AI tools and editors, not only Anthropic's own. The official documentation lives at modelcontextprotocol.io.

The moving parts

  • Host: the application you actually use, such as a desktop chat app or a code editor.
  • Client: the connector inside the host that keeps a connection open to one server.
  • Server: a small program that exposes capabilities, for example "search this repo's docs".

Messages between client and server use JSON-RPC. Servers can run on your own machine (the host starts them as a local process and talks over standard input and output) or remotely over HTTP. Remote servers are what make tools like GitMCP convenient, because there is nothing to install.

What a server can offer

MCP defines three main building blocks:

  • Tools: actions the model can choose to call, like "search code" or "create an issue". Tools can have side effects.
  • Resources: data the model or the app can read, such as a file, a document or a database row.
  • Prompts: reusable templates a user can trigger, for example a standard code-review request.

A worked example

Suppose you ask your editor's assistant: "How does authentication work in this library?" With a documentation server connected, the flow looks like this:

  1. The client asks the server which tools it has, and passes those descriptions to the model.
  2. The model decides a search tool is relevant and requests a call with a query such as "authentication".
  3. The client runs the call, the server returns matching documentation and code snippets.
  4. The model writes an answer based on that returned material instead of guessing from memory.

The result is an answer tied to the real repository, which is far less likely to invent function names that do not exist.

Why MCP matters for developers

Models have a training cutoff. A library released or changed after that cutoff may be missing or misremembered. MCP lets an assistant fetch current documentation on demand. It also lets you reuse the same server across editors and chat apps instead of rebuilding the integration each time.

Limits worth knowing

  • Every connected tool adds description text to the model's context, so connecting dozens of servers can crowd out useful space.
  • A server is code that may run with your permissions. Treat unfamiliar servers with the same care as any software you install. Our MCP security checklist covers this.
  • Retrieval is only as good as the source. A repository with weak documentation gives weak answers.
